# Writing integrations

Integrations ship with `rwv` as Rust modules in `src/integrations/`. This page covers implementing a new one.

For *enabling* an existing integration in a project, see [add an integration](../how-to/add-an-integration.md). For per-integration docs (generated file format, config), see [reference/integrations](../reference/integrations/index.md).

## The `Integration` trait

```rust
pub trait Integration {
    fn name(&self) -> &str;
    fn default_enabled(&self) -> bool;

    fn activate(&self, ctx: &IntegrationContext) -> Result<()>;
    fn deactivate(&self, root: &Path) -> Result<()>;
    fn check(&self, ctx: &IntegrationContext) -> Result<Vec<Issue>>;
    fn activate_hook(&self, ctx: &IntegrationContext) -> Result<()> { Ok(()) }
    fn generated_files(&self, ctx: &IntegrationContext) -> Vec<String> { Vec::new() }
}
```

### Required methods

- **`name`** — unique identifier (e.g., `"npm-workspaces"`). Used in `rwv.yaml` integration config keys.
- **`default_enabled`** — whether the integration runs without explicit opt-in.
- **`activate`** — generate workspace config files and symlinks. Called during `rwv activate`, workweave creation, `rwv sync`, `rwv add`, `rwv remove`.
- **`deactivate`** — remove generated files. Called during workweave deletion and before re-running `activate`.
- **`check`** — read-only inspection. Return `Vec<Issue>` for problems detected. Called during `rwv doctor`.

### Optional methods

- **`activate_hook`** — run install commands to update ecosystem lock files (`npm install`, `uv sync`, `cargo generate-lockfile`) after `activate` has generated config files. Fires whenever the workspace's set of active repos may have changed; users can suppress with `rwv activate --no-install`. Default impl is a no-op. (Previously named `lock` and fired on `rwv lock`; the trigger for ecosystem-lockfile refresh is workspace membership change, which is what `rwv activate` represents.)
- **`generated_files`** — list of paths this integration produces, relative to `output_dir`. Used by the activation framework to detect orphaned files. Default impl returns an empty vec.

## `IntegrationContext`

Each hook receives an `IntegrationContext` with:

| Field | Description |
|---|---|
| `output_dir` | The directory where generated files should be written (project directory for activate; workweave project directory for workweaves) |
| `workspace_root` | The directory where repos live on disk (for manifest detection via `detect_repos_with_manifest`) |
| `project` | The active project name |
| `repos` | Repo entries from the project's `rwv.yaml` |
| `config` | Per-integration config from the `integrations` key in `rwv.yaml` |
| `all_repos_on_disk` | All git repos found on disk under registry directories. Computed once, shared across integrations |
| `all_project_paths` | All project paths. Computed once, shared across integrations |

## Helper methods

- **`ctx.active_repos()`** — filters out `reference` repos (which should not appear in ecosystem workspace configs).
- **`ctx.detect_repos_with_manifest(filename)`** — finds active repos containing a given manifest file (e.g., `"package.json"`), using `workspace_root` for detection.

## Registration

New integrations are registered in `builtin_integrations()` in `src/integrations/mod.rs`. Add a `Box::new(YourIntegration)` entry alongside the existing built-ins; the rest of `rwv` picks it up automatically.

## Style guidelines

- **Auto-detection over explicit config.** Where possible, an integration should detect whether it has work to do (e.g., `npm-workspaces` checks for repos with `package.json`) rather than requiring the user to opt in. Reserve explicit opt-in for cases where auto-detection isn't safe (`gita` is opt-in because it depends on an external tool the user may or may not have installed).
- **No-op on no-match.** If auto-detection finds nothing, generate nothing, raise no error. Activation should succeed.
- **Idempotent.** Running `activate` twice should produce the same result. Running `deactivate` then `activate` should be a clean re-installation.
- **Filter `reference` repos.** Use `ctx.active_repos()` rather than `ctx.repos.iter()` when generating workspace member lists.
- **Declare content ownership.** Every integration is one of: *fully-rwv-owned* (whole-write/whole-delete safe; list in `generated_files()`), *hybrid* (rwv owns a declared key set inside a user-authored file; implement via `ManagedDoc`), or *fully-user-owned* (no content authoring; surfacing only). Do not add a `# Generated by rwv — do not edit` header to hybrid files — those files have user-authored content that must survive `activate` and `deactivate`.
- **Surfacing integrity is framework-level — not a per-integration `check()` responsibility.** `rwv doctor` runs a framework-side Axis-1 surfacing check that asserts every file in the `generated_files() ∪ managed_files()` union has a valid symlink at the weave root. Do not duplicate this logic inside your integration's `check()`. Per-integration `check()` should focus on environment and config preconditions (Axis-2 concerns: missing tools, stale generated content, etc.).
- **Hybrid: use the merge helper.** Implement `activate` as read-merge-write (idempotent; bail loudly on malformed input, never silently overwrite). Implement `deactivate` as strip-owned-keys-then-delete-if-empty; never delete a file that still contains user content. Both halves must land in the same change. Use an explicit ownership marker (not a name-squat): `x-repoweave` for JSON, key decoration for TOML, a comment line for YAML/go.work. See [file-ownership](../explanation/joints/file-ownership.md) for the full contract.
- **Hybrid: test the three shapes.** Activate-preserves (foreign keys survive activate), deactivate-strips-keeps (managed keys gone; foreign keys remain; file kept), deactivate-deletes-if-empty (only managed content existed; file deleted).
