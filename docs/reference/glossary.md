# Glossary

Terminology lookup. For deeper material on each concept, follow the cross-links.

| Term | Meaning |
|---|---|
| **Weave** | A repoweave workspace: any directory containing `projects/` (and typically cloned member repos, `.rwv-active`, and symlinked ecosystem workspace files). |
| **Weave root** | The top-level directory of a weave (or workweave), where `.rwv-active` (or `.rwv-workweave`), `projects/`, `<registry>/<owner>/<repo>/`, and surfaced ecosystem symlinks live. |
| **Primary weave** | The main weave at the weave root (as opposed to a workweave under `.workweaves/`). Named `primary` where a verb or a record names a workspace. |
| **Workweave** | A worktree-based derivative of a weave, created on demand for isolation (agents, features, PR review). Lives at `<parent>/.workweaves/<project>--<name>/` by default. Created, duplicated, and destroyed with `rwv workweave create` (run inside a workweave, it forks from that workweave) and `rwv workweave delete`. |
| **Project** | A directory under `projects/` containing `rwv.toml`, `rwv.lock`, and project-scoped docs. Itself a git repo with normal history. |
| **Project repo** | The git repo at `projects/<name>/`. Carries the manifest, lock, and cross-cutting docs. Does not contain importable code. |
| **Member repo** | A repo listed in a project's `rwv.toml`. Lives at `<registry>/<owner>/<repo>/` as a regular clone in the primary weave and as a git worktree in each workweave. |
| **Member entry** | A repo's table in `rwv.toml`: `type`, `url`, `role`, `branch`, and `recurse-submodules = false` for a member that opts out of populating its submodules. See [formats](./formats.md#repositories-entries). |
| **Declared branch** | The branch a member entry's `branch` names: the one `rwv update --remote` advances, and `rwv clone` and `rwv update` attach. `rwv.lock` records the commit the member is on, never this name. |
| **Weave branch** | A branch of the project repo that carries `rwv.toml` and `rwv.lock`. Each has a **branch record**. |
| **Branch record** | How a weave branch is used: `feature` (work onto a target branch, with `as` the target's own mode when the record was written) or `declared` (members on the branches its member entries declare). Written by `rwv branch set-mode`, `rwv init`, `rwv clone` and `rwv workweave create`, listed by `rwv branch list`. A branch with none is **unrecorded**, and the verbs that align, lock, land or publish refuse it. See [formats](./formats.md#branch-records). |
| **Records branch** | The branch of the project repo (`rwv-records`) that holds one file per weave branch, its record. It has no working tree and no history in common with a weave branch, and is written by compare-and-swap. Its name and every name below it are reserved. Plugins must not write it. |
| **Canonical clone** (or **Canonical store**) | The full git clone at `<primary>/<registry>/<owner>/<repo>/` (or `<primary>/projects/<name>/`) whose `.git` object store backs both the primary weave checkout and every workweave's git worktree. See [clone-topology](../explanation/joints/clone-topology.md). |
| **Minted branch** (ephemeral branch) | The feature branch a workweave created without a branch flag runs on, named `<project>--<workweave>` (with `/` in scoped project names encoded as `+`), in the project repo and in each `owned` or `fork` member. Its record is never published, and it is deleted by the [deletion rule](../explanation/joints/deletion-rule.md) when the workweave is deleted or retired. See [workweave-hierarchy](../explanation/joints/workweave-hierarchy.md). |
| **Manifest** (`rwv.toml`) | Declares which repos belong to a project, their roles, and integration config. See [formats](./formats.md). |
| **Lock file** (`rwv.lock`) | Pins repos to exact 40-character commit SHAs for reproducibility. Derived state — recorded by `rwv lock`, `rwv member add`, `rwv member pin`, `rwv update --remote`, `rwv sync`, and `rwv land`. See [lock-as-derived](../explanation/joints/lock-as-derived.md). |
| **Pin** | A member's commit in a lock. Re-pinning moves it **forward** when the old pin is an ancestor of the new commit or absent, else **backward**; a backward move happens only by name (`rwv member pin`, a setter, or a hand edit of the entry that `rwv lock --commit` commits). A member the lock has no entry for has **no pin** (`pin` `none`). A first pin comes from `rwv member add` (the commit it cloned), `rwv member pin` or `rwv update --remote` (the upstream's tip). `rwv status`, `rwv push` and `rwv doctor` judge a member's pin as a state of the `pin` kind: `none`, `unreachable`, `behind`, `ahead`, `unpinned` or `diverged`. See [doctor findings](./doctor-findings.md#pin). |
| **Activation** | Selecting the active project (writing `.rwv-active`), surfacing weave-root symlinks, running integration install hooks (`--no-materialize` skips hooks), and verifying integration files in `projects/<name>/`. Performed by `rwv activate <project>`, and by `rwv init` and the `rwv clone` or `rwv update` that activates a project; it does not rewrite integration workspace files to pick up `rwv.toml` changes, and it moves no checkout: `rwv activate --update` is the spelling that aligns the project's members first. Inside a workweave, where `activate` is refused, `rwv materialize` runs hooks and repairs symlinks. |
| **Materialization** | Making the ecosystem state the project's membership and pins imply real on disk, without selecting a project: cleaning up artifacts from disabled integrations, repairing weave-root symlinks, settling drifted attested generated files (`--regenerate-drifted`, `--adopt-drifted`), fitting host settings, and running integration install hooks (`npm install`, `pnpm install`, `uv sync`, `cargo fetch`). Performed by `rwv materialize`; the install hooks alone also run in activation and in `rwv workweave create`. `rwv sync` runs none of it. |
| **Active project** | The project named in `.rwv-active`. Single source of truth in the primary weave — no CWD override. |
| **Authoring verb** | A verb that writes the rwv-owned regions of ecosystem workspace files in `projects/<name>/` from `rwv.toml`: `add`, `remove`, `update --remote` and `role`, which change project composition, and `rwv doctor --fix` as a repair. `rwv init <name>` writes a new project's first set. Every other verb (`activate`, `materialize`, `clone`, `fetch`, `pull`, `update`, `workweave create`, `lock`) does not rewrite integration workspace files to pick up `rwv.toml` changes: the ones that activate or materialize a project surface weave-root symlinks, run install hooks and report a missing or drifted file as a warning, and `lock` does none of that. Inside a workweave the authoring verbs run no install hooks. See the [file-ownership](../explanation/joints/file-ownership.md) trigger model. |
| **Hybrid file** | An ecosystem config file in `projects/<name>/` (such as `Cargo.toml`, `package.json`, `pyproject.toml`, `go.work`, `<name>.code-workspace`) where `rwv` owns specific keys or sections, marked as its own (`[workspace]`, `workspaces`, the `use` block), while the user owns the rest of the document. Contrasts with **fully rwv-owned** files, which rwv writes and deletes whole: the gita CSVs, and the lock files ecosystem tools generate during install hooks (`Cargo.lock`, `package-lock.json`), whose accepted content rwv records in `.rwv-owned-digests`. See [file-ownership](../explanation/joints/file-ownership.md). |
| **Role** | A repo's relationship to a project: `owned`, `fork`, `dependency`, `reference`. Encodes change resistance. See [roles](./roles.md). |
| **Integration** | A built-in unit, shipped with rwv, that translates between repoweave's multi-repo model and one ecosystem's workspace format. Bound by a file-ownership contract (surfacing + content ownership). See [integrations](./integrations/index.md) and [file-ownership](../explanation/joints/file-ownership.md). |
| **Plugin** | An external `rwv-<verb>` executable on `$PATH`, dispatched when a verb isn't built into rwv itself. Must not write rwv-owned files; nothing enforces that at dispatch, and `rwv doctor` notices some violations after the fact. Contrast with **Integration**. See [plugin-protocol](./plugin-protocol.md) and [plugin-boundary](../explanation/joints/plugin-boundary.md). |
| **Bundled plugin** | A plugin that ships with `rwv` in every release channel, installed beside the `rwv` binary by the install script, the release archives, Homebrew, `pip`/`uv` and `cargo install --git` alike, such as `rwv-each` ([rwv each](./rwv-each.md)). It is dispatched, addressed and constrained exactly as any other **Plugin**: it learns the checkout from the envelope and the repos from `rwv status --json`, and does not link `rwv`'s internals. |
| **Registry** | The first segment of a repo's canonical path; a short name for where the repo lives. Built-in: `github`, `gitlab`, `bitbucket`, plus `local`, reachable only as an `rwv member add --new` creation address rather than by matching a URL. See [formats — Directory layout](./formats.md#directory-layout). |
| **Canonical tip** | The vetted cross-repo state of a project on a given branch (encoded by that branch's `rwv.lock`). |
| **Lens** | A motivational way of looking at rwv targeted at one audience. Three lenses: [workspace](../explanation/lenses/workspace.md), [monorepo](../explanation/lenses/monorepo.md), [agent](../explanation/lenses/agent.md). |
| **Joint** | A cross-cutting concept that all lenses reference (Diátaxis-explanation, audience-neutral). See [explanation/index.md](../explanation/index.md). |
| **Merge source** | What a feature's member takes in at `rwv sync`: the tip of the branch the member lands on, the newer of that branch and its upstream, or the target's pin where that branch exists nowhere. |
| **History setting** | How a target accepts work, from its own `rwv.toml`: `history = "linear"`, `"merge"` or `"ff-only"` at the top level, overridden per member by a member entry's `history`. It governs `rwv sync` taking the target in and `rwv land` landing into it; there is no default. `rwv branch set-history` writes it; `--history` supplies one for one run only where the target records none. See [history and lineage](../explanation/joints/history-and-lineage.md#the-history-setting). |
| **Lineage rule** | `rwv sync`, `rwv land` and `--merge-upstream` move a member holding new work only when the branch it lands on contains the work's base, the newest commit of its first-parent chain that a lock in the target's history pins; otherwise they refuse as `pin` `off lineage`. See [history and lineage](../explanation/joints/history-and-lineage.md#the-lineage-rule). |
| **Retire** | `rwv land --retire`: once the landing is done, delete the workweave and apply the deletion rule to the feature's branches. The flag is on `rwv land`, not `rwv sync`. |
| **Parent (of a workweave)** | The workspace the workweave was forked from. Recorded in `.rwv-workweave`'s `parent` field. |
| **Land** | `rwv land`: land the checked-out feature into its target. The work is composed in the source workspace as the target's history setting says, the lock is recorded in one project commit, and the target and each receiving branch fast-forward to exactly what was composed. Contrast with `rwv sync`, which takes the target's work into the feature. See [landing](../explanation/joints/landing.md). |
| **Target** | The branch a feature's record says it lands into. `rwv sync` takes it in and `rwv land` lands into it; `--target <T>` names another for one run. See [records and modes](../explanation/joints/branch-records.md). |
| **Receiving branch** | Where a member lands: its branch named after the target when the target is a feature, else the branch the merged entries declare. See [landing](../explanation/joints/landing.md). |
| **Dependents** | The weave branches whose records land into a branch. A branch with dependents is not deleted, and a rebase of it carries them or refuses. See [history and lineage](../explanation/joints/history-and-lineage.md#stacks). |
| **Landed** | A branch has landed on a target when it is an ancestor of the target's branch. Nothing else proves it: a forge's squash is confirmed by name. |
| **Expected state** | Where a member sits for the checked-out branch: its branch, or detached at its pin, as the record, the entries and the lock say. A member in its expected state is **aligned**. See [alignment](../explanation/joints/alignment.md). |
| **Unrecorded** | A weave branch with no record. The verbs that align, lock, land or publish refuse it until a spelling names its record. |
| **Stop** | An operation halted by a conflict, a failed check, a lost race or a crash, its op record kept. It ends with `--continue` or `rwv abort`. See [stops and abort](../explanation/joints/stops-and-abort.md). |
| **Operator branch** | A member's local branch holding unpushed commits that nothing else accounts for: checked out nowhere, named after no recorded weave branch and declared by none. `rwv status` lists it and prints no choice. |
| **Selector** | The shared `--role` / `--repo` flag surface on `fetch`, `pull`, `update`, `push`, `status`. See [reference/cli — Selector grammar](./cli.md#selector-grammar). |
| **Savepoint** | A git ref under `refs/rwv/pre-op/<op-id>` (`refs/rwv/pre-op/<op-id>-target` in a `land`'s target workspace) snapshotting one ref an operation may move before it moves: a checkout's tip and the branch it is on, or a branch a landing moves without a checkout. Used by `rwv abort` to roll back. |
| **Backup** | A git ref at `refs/rwv/backup/<branch>/<id>` that an rwv verb makes before any step that would leave a commit or an uncommitted edit reached by no branch, no remote-tracking branch and no other backup. Unlike a savepoint it outlives the operation, and only `rwv backup drop` or `rwv backup prune` removes it. See [`rwv backup`](./cli.md#rwv-backup). |
| **Backup slot** | One of the two backups `rwv abort` keeps per branch and per checkout: `<branch>/aborted` holds the tip abort last reset that branch from, and `<branch>/aborted-working-copy` the working copy abort last discarded in the checkout on that branch. The next abort that keeps something there overwrites it. See [`rwv abort`](./cli.md#rwv-abort---leave-target---discard-unreadable-record). |
| **Pin rule** | No backup is dropped when that would leave a commit some project's live lock pins reached by no branch, remote-tracking branch or backup. A pin is live in every project of the weave, not only the one the verb runs in. See [`rwv backup drop`](./cli.md#rwv-backup-drop-repo-name). |
| **Url remote** | Of a member, the remote of its clone that has the member's `url`. A verb that fetches adds it first when the clone lacks it, named by the url's owner segment; a name another url already holds refuses as `name` `taken`. Of the project repo, the remote `rwv clone` or `rwv init --provider` created it with, or `rwv member set-url projects/<name>` recorded, kept in the clone's own configuration; else its only remote while it has exactly one; else none. |
| **Push target** | Where a branch publishes, in git's order: the branch's push remote, the repo's default push remote, the remote the branch takes in from, and last the url remote. A branch with none of them has no push target, and `rwv push` refuses it before anything is pushed. |
| **Push branch** | The same-named branch on a branch's push target, as last fetched. A branch stands to it as even, behind, ahead or diverged, by ancestry; with none, the branch is unpublished, or gone when its upstream was deleted. |
| **Home remote** | Where a new branch is taken from: the remote configured for it (git: `checkout.defaultRemote`), else the url remote. |
| **Upstream** | The remote branch a branch takes in from. One of another name than the branch's own is a foreign upstream, which `rwv push` refuses. |
| **Op-state** | The on-disk record of an in-flight `rwv sync`, `rwv land`, `rwv cherry-pick`, or `rwv pull` or `rwv update --remote` with `--merge-upstream` or `--reset-to-upstream`. Comprises an owner record (`.rwv-op`) at the initiating workspace and zero or more thin leases (`.rwv-op-lease`) at other mutated workspaces. Preserved on phase failure; cleared on success or after `rwv abort`. See [formats](./formats.md#rwv-op--owner-op-record). |
| **Owner record** | The full op record (`.rwv-op`) written at the initiating workspace. Holds all op parameters, the current phase, converged tips, and named overrides. The sole copy of mutable op state — leases at other workspaces point back to it. See [formats](./formats.md#rwv-op--owner-op-record). |
| **Owner workspace** | The workspace that holds the owner record for a given op — the workspace the operation was started in. `rwv abort` and `--continue` invoked from a non-owner workspace follow the lease pointer to find it; `rwv abort` rolls back both workspaces from either one. |
| **Lease** | A thin immutable file (`.rwv-op-lease`) written at every workspace an op mutates other than the owner. Provides mutex semantics (prevents concurrent ops) and a pointer to the owner workspace. See [formats](./formats.md#rwv-op-lease--thin-lease-pointer). |
| **`--json` envelope** | The shape `{"$schema": "...", "<key>": [...]}` emitted by JSON-capable verbs, the same whatever `-j` is. Key is verb-specific. See [reference/cli — JSON envelope convention](./cli.md#--json-envelope-convention). |
| **Drift (index / working-tree)** | A repo's index or on-disk files don't match its HEAD tree — e.g. when a branch ref checked out in a workspace is moved externally without updating that workspace's index and working tree. See [shared-refs-drift](../explanation/joints/shared-refs-drift.md). |
| **Lock merge driver** | The merge driver that merges `rwv.lock` in a merge rwv does not make, pins three-way: for git, the `rwv.lock merge=rwv-lock` line in the project repo's committed `.gitattributes`, with `merge.rwv-lock.driver` naming `rwv lock --merge-driver %O %A %B` in the clone's config. rwv's own merges and replays hold it and settle the lock themselves. Doctor reports one that is absent or set up by an earlier release as `missing-lock-merge-driver`. See [`rwv lock`](./cli.md#the-lock-merge-driver). |
| **Basedir** | The directory new workweaves of a project are created in, recorded per project in the workweave index the project clone keeps. Defaults to `<parent-of-primary>/.workweaves`; `rwv workweave set-default-create-basedir <path>` records another, `create --basedir <path>` replaces it for one run, and `create --dir <path>` places one workweave at exactly that path. `rwv doctor` calls a project's basedir its *container*. |
| **Surfacing** | Linking a file that lives in `projects/<name>/` to the weave root, where ecosystem tools look for it (`Cargo.toml -> projects/<name>/Cargo.toml`). Surfaced links belong to rwv, and the file they point at to whoever authored it. Doctor reports a link out of step as `surfacing`. See [symlinks-as-structure](../explanation/joints/symlinks-as-structure.md). |
| **Attest** | Record the digest of a generated file's accepted content, with the digests of the inputs it was derived from, in `.rwv-owned-digests`. An attested file whose bytes later differ is reported as `managed-file-drift` and is not regenerated over without consent; one whose inputs moved is `derived-state-stale`. |
| **Deletion rule** | What decides which branches `rwv branch delete`, `rwv workweave delete` and `rwv land --retire` delete. A branch belongs to the deleted branch `W` if it is the project branch `W`, or a listed member's branch named `W` that no live weave branch declares. It is deleted when everything on it has landed on the branch `W` lands into, no live lock pins a commit only it reaches, and (for the project branch) no member branch that belongs survives. `--discard-unlanded` lifts the landed condition after a backup. See [`rwv branch delete`](./cli.md). |
| **Survivor** | A branch the deletion rule kept, reported with its reason (`unlanded`, `pinned`, `open-head`, `members`, `unconfirmed`). A delete that leaves one exits with status `3`. |
| **Consent flag** | A flag that permits one named consequence a verb otherwise refuses, such as `--discard-uncommitted`, `--adopt-drifted` or `--leave-target`. Each names the loss it accepts; there is no blanket override. See [destructive operations](../explanation/destructive-operations.md). |

## Facts

A **fact** is a statement of what the refs show, listed beside a state in `rwv status`, a refusal and the `facts` of `--json`. A fact never selects a choice or changes what a verb does; it is evidence for the operator's decision.

| Fact | What it says |
|---|---|
| `rewritten` | A superseded tip is recorded for the branch: a fetch moved its upstream or push branch off a tip the branch still holds, which is how a rewrite of the remote's history shows. |
| `landed` | The branch is an ancestor of the branch it lands into. |
| `pinned-by` | Another project's live lock pins the commits, so they are not unpinned. |
| `shared` | Other live weave branches declare the member branch, so a landing into it moves them too. |
| `pin-landed` | The pin is on the branch it lands into. |
| `checkout` | The member was left detached because its branch is checked out in another workspace, named. |
| `patch-equivalent` | The unlanded commits carry changes equivalent to commits on the branch they land into, commit by commit or as one squashed change; it names them. It is evidence for a confirmation such as `--discard-unlanded` or `--reset-to-target` and never replaces it. |
| `ahead`, `behind` | How many commits the branch holds that its push branch lacks, and the reverse. |
