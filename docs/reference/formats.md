# File formats

Reference for the on-disk files repoweave reads and writes.

## `rwv.yaml` — project manifest

The source of truth for which repos belong to a project. Committed in the project repo at `projects/<name>/rwv.yaml`.

```yaml
repositories:
  github/chatly/server:
    type: git
    url: https://github.com/chatly/server.git
    version: main
    role: owned
  github/chatly/web:
    type: git
    url: https://github.com/chatly/web.git
    version: main
    role: owned
  github/chatly/protocol:
    type: git
    url: https://github.com/chatly/protocol.git
    version: main
    role: owned
  github/socketio/engine.io:
    type: git
    url: https://github.com/chatly/engine.io.git
    version: main
    role: fork

integrations:
  npm-workspaces:
    enabled: false
  pnpm-workspaces:
    enabled: true
```

### `repositories` entries

Keyed by canonical local path (`<registry>/<owner>/<repo>`). Each entry:

| Field | Required | Description |
|---|---|---|
| `type` | yes | VCS type. Currently `git`. |
| `url` | yes | Clone URL. Used by `rwv fetch` on other machines. |
| `version` | yes | Branch or tag (manifest); revision SHA (lock). |
| `role` | yes | One of `owned`, `fork`, `dependency`, `reference`. |

Both `role: owned` (canonical) and `role: primary` (legacy alias) parse. The tool always writes `role: owned`. See [reference/roles — Compatibility](./roles.md#compatibility-primary-as-a-legacy-alias-for-owned) for the migration path.

Format is based on vcstool's `.repos` format, extended with `role` and optional `integrations`.

### `integrations` block

Optional. Only overrides need to be listed — integrations not mentioned use their own defaults.

```yaml
integrations:
  npm-workspaces:
    enabled: false
  pnpm-workspaces:
    enabled: true
  static-files:
    enabled: true
    files: [turbo.json, .eslintrc.json]
```

Per-integration config keys vary; see [reference/integrations](./integrations/index.md).

## `rwv.lock` — pinned revisions

Generated by `rwv lock` or `rwv update`. Same format as `rwv.yaml` but `version` holds resolved revisions. When a tag exists at HEAD, the tag name is recorded; otherwise the revision SHA.

```yaml
# projects/web-app/rwv.lock — generated, committed
workweave: agent-42    # or omitted for the weave
repositories:
  github/chatly/server:
    type: git
    url: https://github.com/chatly/server.git
    version: v2.1.0              # tagged — human readable
  github/chatly/web:
    type: git
    url: https://github.com/chatly/web.git
    version: e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0  # untagged — revision SHA
  github/chatly/protocol:
    type: git
    url: https://github.com/chatly/protocol.git
    version: 7a3b2c1d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b
```

| Field | Description |
|---|---|
| `workweave` | Optional. Records which workweave generated the lock. Omitted for the primary weave. |
| `repositories[].version` | Tag name (released) or SHA (unreleased). The format itself encodes release state. |

`rwv.lock` is derived state. Do not hand-edit; it is the *output* of `rwv lock` and the *output* of `rwv sync` Phase 3. See [lock-as-derived](../explanation/joints/lock-as-derived.md).

`sha256sum rwv.lock` is the project fingerprint — two machines with the same checksum have identical source for every repo.

Each workspace (primary weave or workweave) owns its own `rwv.lock`. A `rwv lock` from a workweave updates the workweave's lock, not primary's.

## `.rwv-active` — active project marker

Lives at the weave directory root. Single line: the active project name.

```
web-app
```

`.rwv-active` is the **single source of truth** for the active project within a workspace. There is no CWD-based override; `cd projects/<name>/` does not switch projects.

Updated by `rwv activate <project>`. Action verbs (`rwv lock`, `rwv add`, `rwv sync`) read it; pass `--project <name>` for a one-shot override without changing the file.

## `.rwv-workweave` — workweave marker

Lives at every workweave directory root. Records the workweave's identity and parent.

```yaml
primary: /home/user/work
project: web-app
parent: /home/user/work/.workweaves/web-app--feat
```

| Field | Description |
|---|---|
| `primary` | Absolute path to the primary weave |
| `project` | Project name this workweave is forked for |
| `parent` | Absolute path to the workspace the workweave was forked from. `primary` value when forked from primary; the parent-workweave path when forked from inside another workweave |

Legacy markers (pre-parent-field) parse cleanly — the read path backfills `parent` to `primary`.

Consumed by:

- `rwv sync` (bare) — targets the recorded parent.
- `rwv sync --retire` — verifies convergence with parent before deleting.

See [workweave hierarchy](../explanation/joints/workweave-hierarchy.md) for one-hop semantics.

## Directory layout

repoweave uses a flat, provenance-based layout for repos: `{registry}/{owner}/{repo}/`. Project directories live under `projects/{name}/`.

```
~/work/                                       # weave directory
├── github/
│   ├── chatly/
│   │   ├── server/                           # manifest repo (clone)
│   │   ├── web/                              # manifest repo
│   │   └── protocol/                         # manifest repo
│   └── socketio/
│       └── engine.io/                        # manifest repo (fork)
│
├── projects/
│   ├── web-app/                              # project repo
│   │   ├── rwv.yaml
│   │   ├── rwv.lock
│   │   ├── package.json                      # generated workspace file
│   │   ├── package-lock.json                 # ecosystem lock file
│   │   └── docs/
│   └── mobile-app/
│       ├── rwv.yaml
│       ├── rwv.lock
│       └── docs/
│
├── package.json -> projects/web-app/package.json       # symlink to active project
├── package-lock.json -> projects/web-app/package-lock.json
├── go.work -> projects/web-app/go.work
├── go.sum -> projects/web-app/go.sum
├── node_modules/                             # tool state — gitignored
├── .venv/                                    # tool state — gitignored
├── .rwv-active                               # "web-app"
├── .gitignore
│
└── .workweaves/                              # workweaves live here
    └── web-app--payments/                    # one workweave
        ├── github/chatly/server/             # worktree
        ├── github/chatly/web/                # worktree
        ├── projects/web-app/                 # worktree
        ├── .rwv-active                       # "web-app"
        └── .rwv-workweave                    # parent: ~/work
```

The first path segment is a **registry** — a short name for where the repo lives. Built-in registries: `github` → `github.com`, `gitlab` → `gitlab.com`, `bitbucket` → `bitbucket.org`. Custom registries are configured in `rwv`'s own config (domain-based for hosted hosts, directory-based for local paths).

- **Repos are regular clones.** `cd github/chatly/server && git status` works. No bare repos, no `.git` file indirection.
- **Ecosystem files are symlinked** at the weave directory to the active project's directory. Real files live in `projects/<name>/`.
- **Ecosystem lock files are committable** alongside `rwv.yaml` in the project directory.
- **Project repos** have `rwv.yaml` and `rwv.lock`. They don't contain importable code — build tools never look at `projects/`.
- **Tool state directories** (`node_modules/`, `.venv/`, `target/`) are at the weave root, gitignored, regenerated by the ecosystem install commands.

### Project paths

Project paths default to `projects/{name}/`. If names collide across organizations, `rwv fetch` errors and suggests a scoped form: `projects/{owner}/{name}/` or `projects/{registry}/{owner}/{name}/`.

`rwv` commands that take a project path require the path *as created* — if the project lives at `projects/chatly/web-app/`, use `chatly/web-app`, not `web-app`.
